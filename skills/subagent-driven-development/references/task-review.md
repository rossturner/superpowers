# Reviewing a Task

Part of superpowers-ross:subagent-driven-development. Read this before dispatching the two reviewers for each task. SKILL.md says who the reviewers are and that they are dispatched together, in one message.

- Hand the reviewers their diff as a file: run this skill's `bash scripts/review-package PLAN_FILE BASE HEAD` by its absolute path, from the working tree you're executing in, and pass the reviewer the file path it prints (or, without bash: `git log --oneline`, `git diff --stat`, and `git diff -U10` for the range, redirected to one uniquely named file, with `# Review package: BASE..HEAD (<L> lines)` as its first line). Both reviewers get the same path. The output never enters your own context, and each reviewer reads the commit list, stat summary, and full diff with context from one file, in ~1,000-line chunks. Use the BASE you recorded before dispatching the implementer — never `HEAD~1`, which silently truncates multi-commit tasks. Never dispatch a reviewer without a diff file.
- **Reviewer inputs:** both reviewers get the brief file, the report file, the review package, and the global constraints that bind the task. The spec reviewer also gets the spec path, the invariants list verbatim, and the names of the invariants whose governed paths this task's outcome touches. Name them generously: an invariant you leave off is one the reviewer may not search.
- **Read-through check:** every reviewer report — task review, re-review, final review — states "read through line L". A report without that statement, or with an L short of the package's line count, is re-dispatched once. If the second report also lacks it, rule on what the review covered (accept it, or treat the unread part as unreviewed) and ledger the ruling.
- The global-constraints block you hand the reviewers is their attention lens. Copy the binding requirements verbatim from the plan's Global Constraints section or the spec: exact values, exact formats, and the stated relationships between components ("same layout as X", "matches Y"). The reviewer templates already carry the process rules (YAGNI, test hygiene, review method) — the constraints block is for what THIS project's spec demands.
- Do not add open-ended directives like "check all uses" or "run race tests if useful" without a concrete, task-specific reason. The invariants are that reason, written down: the spec reviewer's search is scoped to them.
- Do not ask a reviewer to re-run tests the implementer already ran on the same code — the implementer's report carries the test evidence
- Do not pre-judge findings for the reviewer — never instruct a reviewer to ignore or not flag a specific issue. If you believe a finding would be a false positive, let the reviewer raise it and adjudicate it in the review loop. If the prompt you are writing contains "do not flag," "don't treat X as a defect," "at most Minor," or "the plan chose" — stop: you are pre-judging, usually to spare yourself a review loop.
